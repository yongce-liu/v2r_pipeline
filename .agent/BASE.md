# BASE.md

## 1. 基本原则

开发工作优先保证：

1. 正确性；
2. 用户数据和现有工作的安全；
3. 可维护性；
4. 可复现性；
5. 可观测性；
6. 实现简洁性；
7. 运行效率。

不得为了追求代码量少、短期速度或表面通过，而牺牲正确性、可读性、可验证性或数据安全。也不得写过多的无意义fallback和安全检查代码。必要时候可以删除旧逻辑来保证代码简洁易读。

## 2. Python 环境与依赖管理

- 使用 `uv` 管理 Python 环境、依赖和命令执行。
- 项目依赖统一声明在 `pyproject.toml` 中。
- 依赖变更后同步更新并提交 `uv.lock`。
- 不使用临时 `pip install` 修改项目环境。
- 不直接修改 `.venv`、`site-packages` 或第三方依赖源码。
- 不使用未固定的 `main`、`develop`、`master` 或 `latest` 作为正式依赖版本。
- 对影响运行行为、数值结果或兼容性的依赖，应固定明确版本或 commit。
- 仅在标准库和已有依赖无法满足需求时新增依赖。
- 新增依赖时，应说明用途、必要性和可能影响。
- 不为单一简单功能引入大型框架。

推荐使用：

```bash
uv sync
uv run <command>
uv run --no-sync <command>
```

仅当环境已同步且当前操作不应修改锁文件时使用 `--no-sync`。

## 3. 命令行规范

- 命令行接口统一使用 `tyro`。
- 参数使用带类型标注的 `dataclass` 定义。
- 每个可执行命令应提供显式 `main()` 入口。
- 命令入口只负责参数解析、配置构建和业务函数调用。
- 核心逻辑不得全部堆积在 CLI 入口中。
- 模块导入时不得自动执行耗时操作、下载资源或写入磁盘。
- 文件路径统一使用 `pathlib.Path`。
- 不在代码中写死本地路径、设备编号、用户名或环境相关信息。
- 参数名称应清晰、稳定，并避免双重否定。
- 帮助信息应说明参数用途、单位、默认值和输入输出含义。
- 不创建没有实际功能的占位命令。

## 4. 配置管理

- 项目运行配置统一使用 YAML（`.yaml`/`.yml`），不得新增 TOML 运行配置；`pyproject.toml` 仅用于 Python 标准项目元数据和工具配置。
- 所有会影响程序行为的配置都应显式可见。
- 不将关键配置隐藏在模块级全局变量中。
- 配置对象应有类型标注。
- CLI 参数可以覆盖默认配置，但覆盖结果必须可追踪。
- 程序需要修正或补全配置时，应保留原配置，并输出最终生效配置。
- 不静默修改用户提供的配置文件。
- 路径、随机种子、设备、并发数和输出目录等应由配置控制。
- 密钥和敏感信息不得写入代码或提交到 Git。

## 5. 日志规范

- 应用日志统一使用 `loguru`。
- 不使用 `print()` 代替调试日志。
- 只有当标准输出本身是明确的机器可读输出协议时，才允许使用 `print()`。
- 日志应包含足以定位问题的阶段、输入对象和操作上下文。
- 不在高频循环中持续输出 `INFO` 日志。
- 批处理中的单项失败若允许继续，必须记录失败对象和错误原因。
- 需要保留堆栈时使用 `logger.exception()`。
- 不记录密钥、完整环境变量或不必要的隐私信息。
- 文件日志应写入指定输出目录，不默认写入仓库根目录。

日志级别建议：

- `DEBUG`：内部状态、详细参数和诊断信息；
- `INFO`：阶段切换、配置摘要和汇总结果；
- `WARNING`：可恢复问题、异常输入或降级行为；
- `ERROR`：单项任务失败或无法完成的操作；
- `CRITICAL`：导致整个流程无法继续的严重错误。

## 6. 编码规范

- 使用 4 空格缩进。
- 文件、函数和变量使用 `snake_case`。
- 类名使用 `CamelCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 文件路径使用 `pathlib.Path`。
- 公开接口和阶段间数据结构应提供类型标注。
- 复杂返回值优先使用 `dataclass`、`NamedTuple` 或明确的数据结构。
- 不使用隐式可变全局状态。
- 随机行为必须接收显式 seed 或 RNG。
- 函数应保持职责单一，但不把简单逻辑过度拆分。
- 只在真实扩展点使用接口、工厂、注册表或适配器。
- 注释用于解释原因、约束、单位和非显然行为，不重复代码表面含义。
- 优先复用项目已有模式，不为个人偏好引入另一套风格。

## 7. 项目结构与包组织

- 项目以标准可安装 Python 包的形式组织，通过 `pyproject.toml` 声明打包配置，不依赖临时的 `sys.path` 拼接或当前工作目录来定位模块。
- 打包构建后端统一使用 `hatchling`（`build-backend = "hatchling.build"`），不使用 `setuptools`。
- 第一方代码统一放在单一顶层包 `v2sim2va/` 下，并按 `core`、`perception`、`reconstruction`、`scene`、`retarget`、`sim`、`render`、`data` 等领域划分子包；不得为这些内部模块重新建立 `src/*` workspace package。
- 顶层包按功能划分子包（如数据、模型、仿真、工具等），每个包目录包含 `__init__.py`。
- 供用户直接使用的入口模块（训练、推理等）放在包根目录，实现细节下沉到对应功能子包。
- 包内部引用统一使用以顶层包名开头的绝对导入（如 `from <pkg>.models import ...`），不使用裸子模块名（如 `from models import ...`）依赖运行目录解析。
- 可执行入口通过 `pyproject.toml` 的 `console_scripts` 声明，并提供无参入口函数供其调用。
- 仅当引入的确为包外部代码（第三方或外部仓库）且必须通过路径注入时，才保留受限且集中的 `sys.path` 处理，并在注释中说明来源与原因。

## 8. 命名规范

- 文件、模块、目录命名不与其所在包名或父目录名冗余重复；已由包/目录路径表达的语义不再在文件名中复述（例如包 `foo` 下的入口用 `train.py` 而非 `foo_train.py`）。
- 命名应能从其所在的模块路径中获得完整语义（`foo.train` 已足够清晰）。
- 命名以简洁、稳定、可从上下文推断为准，避免为消歧而堆砌前缀。
- 重命名模块或文件时，必须同步更新所有引用点：包内导入、`pyproject.toml` 入口（`console_scripts`）、脚本中的 `-m` 调用路径，以及文档中的路径引用。

## 9. uv 项目与隔离运行时

- 主项目保持单一 `pyproject.toml`、单一 `v2sim2va` 包和统一 `uv.lock`，内部领域模块不拆成 workspace members。
- 若两个运行时存在不可调和的 Python、CUDA、PyTorch 或二进制依赖冲突，不得为了“单环境”强行合并；应拆成独立的 uv project，并通过稳定的文件、命令行或进程接口交互。
- `runtimes/` 中的隔离项目不是主包 workspace member，不通过 `PYTHONPATH` 或 editable install 与主包耦合。

## 10. 阶段边界与数据契约

- 跨模块数据必须通过明确的数据契约传递，不依赖调用方了解被调用模块的内部目录结构。
- 阶段输出应包含：
  - 数据本体；
  - schema/version；
  - 生成该结果所使用的关键配置；
  - 上游输入标识；
  - 必要的质量指标或有效性标记。
- 不允许下游模块通过猜测文件名、扫描临时目录或读取上游私有缓存来获取输入。
- 对大型二进制数据可使用路径引用，但路径引用必须由 manifest 或显式返回值提供。
- 数据 schema 发生不兼容变更时应提升 schema version，不静默复用旧格式。
- 能够复用的阶段输出应支持缓存和断点续跑；缓存命中必须校验输入和关键配置是否一致。

## 11. 坐标系、单位与时序

- 所有 3D 数据必须明确记录坐标系名称、变换方向和单位。
- 变换命名优先采用 `T_<target>_<source>`，表示把 source 坐标中的点变换到 target 坐标。
- 位移默认使用米，角度内部计算默认使用弧度；若接口使用其他单位，必须在字段名、类型或文档中明确标识。
- 四元数必须明确元素顺序，例如 `wxyz` 或 `xyzw`，不得依赖库默认值进行隐式转换。
- 图像坐标必须明确像素原点和轴方向；相机模型必须明确内参定义和畸变模型。
- 连续时间数据必须有统一时间基准；不得仅依赖数组下标推断真实时间。
- 多传感器、多视频或仿真数据对齐时，应以显式 timestamp/fps/timebase 作为依据。
- 插值、重采样和滤波必须说明目标频率及边界行为。

## 12. 第三方代码、模型与资产

- 第三方仓库优先作为明确版本的依赖、git submodule 或独立 runtime 集成，不复制大段源码进入项目包。
- 若必须 patch 第三方代码，应集中维护 patch/fork，并记录：
  - upstream 来源；
  - 固定 commit；
  - 修改原因；
  - license。
- 模型权重、机器人资产、纹理和大型数据不直接提交到普通 Git 历史。
- 下载的模型或资产应校验版本，重要资源建议记录 hash。
- 不自动接受未知 license 的数据、模型或资产进入可发布产物。
- 运行时下载必须可显式关闭，生产流程不依赖不可追踪的在线最新版本。
- 机器人本体和末端执行器资产必须分离保存并通过 YAML 注册表选择；不得在 Python 中拼接、改写或硬编码生成 URDF/MJCF。无法由仿真库组合时，应在 `assets/robots/` 中保存可直接加载的完整 URDF/XML。
- 项目生成的 MP4 视频统一使用 VS Code 可直接预览的 H.264 编码、YUV420p 像素格式，并启用 fast-start 元数据布局。

## 13. 数值算法与物理计算

- 优先保留问题本身的物理量和几何约束，不使用仅为“让结果看起来合理”的隐藏修正。
- 优化、IK、滤波、插值和物理仿真必须暴露关键容差、权重、迭代次数和停止条件。
- 数值失败应区分：
  - 输入无效；
  - 优化未收敛；
  - 约束不可满足；
  - 数值异常；
  - 运行时资源错误。
- 不将 `NaN`、`Inf`、空轨迹或越界姿态静默写入正式输出。
- 对插值、裁剪、clamp、fallback pose 等行为必须可追踪，并输出对应质量标记。
- 几何 mesh 的 visual geometry 与 collision geometry 应逻辑分离，不能因碰撞简化破坏可视化资产。

## 14. GPU、并发与资源管理

- 设备选择必须由配置控制，不在库代码中写死 `cuda:0`。
- GPU 模型初始化应集中管理，避免在逐帧或逐样本循环中重复加载。
- 长视频或批处理任务应采用流式读取或有界缓存，避免把全部帧、全部 mesh 或全部中间 tensor 长期保存在内存/显存。
- 进程并发数、worker 数和队列大小必须可配置，并设置合理默认值。
- CPU 多进程、CUDA 多进程或第三方渲染器同时使用时，应明确进程模型，不依赖隐式 fork 行为。
- 任务结束后应释放文件句柄、视频解码器、viewer、renderer 和 GPU 上下文等外部资源。

## 15. 测试与验收

- 每个独立包至少包含：
  - import/smoke test；
  - 核心数据结构或算法的单元测试；
  - 一个最小可运行 CLI 测试。
- 几何与机器人相关代码应增加可验证的不变量测试，例如：
  - 坐标变换往返误差；
  - 四元数归一化；
  - FK/IK 误差；
  - joint limit；
  - 时间戳单调性；
  - mesh 单位和尺度。
- Pipeline 阶段应有小样本集成测试，禁止只依赖完整大模型流程验证正确性。
- 修复 bug 时优先增加能够复现该 bug 的回归测试。
- 测试不得依赖开发者个人路径、已有缓存或未声明的在线资源。

## 16. 输出、缓存与可恢复执行

- `inputs/` 视为只读输入，不覆盖用户原始数据。
- 正式输出、缓存和临时文件必须分离。
- 默认不得覆盖已有正式输出；需要覆盖时必须由显式参数允许。
- 每个长流程阶段应尽量做到幂等：相同输入和配置重复执行，不产生不可解释的额外副作用。
- 支持断点续跑时，只能复用经过完整性校验的阶段产物。
- 临时文件应先写入临时路径，成功后再原子移动到最终路径，避免中断后留下看似完整的损坏文件。
- 输出目录中应保存本次运行的最终生效配置和软件版本摘要。

## 17. Agent 实现约束

- 实现前先阅读项目中的目标、设计和计划文档，不从目录名自行猜测需求。
- 不一次跨越多个尚未稳定的数据契约实现大段 pipeline。
- 每完成一个阶段，先验证其输入输出契约，再开始依赖它的下一阶段。
- 若实现过程中发现设计文档与真实依赖、数据或物理约束冲突，应先更新设计说明，再修改实现。
- 不为了兼容尚未存在的未来需求提前加入抽象层；仅为已经明确的第二实现、第二后端或真实扩展点建立接口。
- 不保留没有明确当前用途的 legacy 兼容路径；迁移到新契约后，应删除旧入口、旧字段适配和未使用代码，而不是继续维护双通道逻辑。
